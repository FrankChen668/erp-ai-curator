# ERP AI Curator — Project North Star

> Current product contract. Detailed working model: `docs/AI_LEVERAGE_MODEL_V3.md`.

## 1. 项目为什么存在

ERP AI Curator 面向 **泛 ERP / 企业信息化从业者**，而不是只面向 SAP / Oracle 产品顾问。

覆盖的工作环境可以包括：

- SAP / Oracle 等标准 ERP；
- SAP / Oracle 二开与集成；
- Java / .NET 等技术栈建设的定制供应链、财务、采购、制造等企业系统；
- ERP 周边平台、接口、数据、测试与运维工作。

目标角色包括实施 / 业务顾问、项目经理、产品经理、解决方案人员和开发人员。

真正要解决的问题是：

> **面对一个真实企业信息化工作任务，AI 应该怎样介入？普通通用 AI 是否已经够用？如果值得引入专门能力，现成的 Skill / Tool / 方法 / 教程中什么最值得采用？**

因此项目不是 AI 工具大全，也不只是资源搜索器。

## 2. 一句话定义

> **泛 ERP / 企业信息化工作的 AI 工作方式导航器：从真实任务出发，优先吸收互联网上已经存在的实战经验与现成能力，把高噪声资源压缩成少量真正值得学习、采用和分享的方案。**

主链路：

`真实任务 → AI 杠杆判断 → 第三方实操/经验发现 → 原始 Skill/Tool 核验 → 必要的官方事实兜底 → 少量可执行建议`

搜索只是其中一个按需动作；重复造教程、重新发明已有工作法、为每个候选做实验室式验证都不是产品目标。

## 3. 上游永远是真实工作问题

项目必须从真实工作问题开始，而不是从已有资源反推使用场景。

有效输入优先级：

1. `REAL_USER`：真实从业者原始问题（问卷、访谈、实际求助）
2. `OWNER_REAL`：项目负责人自己真实遇到的问题
3. `REPRESENTATIVE`：为了覆盖边界而设计的代表性题目
4. `SYNTHETIC`：纯测试构造题

前两类用于产品证据；后两类只用于边界测试和回归。

不把真实问题先改写成“适合 Skill 的标准场景”。

当需要归一化真实问题用于搜索和验证时，优先保留这个结构：

```text
真实情境
+ 手头已有项目材料
+ 当前必须完成的动作
+ 下一份明确交付物
+ 时间 / 评审 / 数据边界
```

例如，“需求分析”不是足够具体的产品单位；“客户访谈结束后，拿会议纪要、流程和附件在第二天上午形成可评审需求包”才是。

当前问卷中的重复真实问题可归一化为 Problem Cards，但 Problem Card 只是保存真实任务结构，不是永久场景 taxonomy。

## 4. Skill 的核心不是场景枚举，而是 AI 杠杆判断

不为 SAP、Oracle、供应链、财务、项目管理、开发分别建设一套固定规则。

面对任何任务，先判断：

1. 用户到底要交付什么结果；
2. 当前最大的时间 / 质量 / 学习成本在哪里；
3. 有哪些真正会决定方案可用性的硬约束，例如数据/源码能否离开环境、本地/云端限制、特定可编辑格式、系统权限、版本和成本；
4. 普通通用 AI 是否已经足够；
5. 是否存在专门能力能明显改善结果；
6. 如果需要专门能力，应该补的是 Tool、Skill、方法、知识源还是工作流。

泛化能力来自这套判断，而不是来自预先罗列几百个场景。

专业业务、配置、代码和接口知识即使走通用 AI，也应优先基于用户材料、项目文档、代码、配置或可信知识源做 **source-grounded analysis**，而不是依赖模型记忆。

## 5. 三种合法结果

### A — 通用 AI 足够

不搜索、不凑资源。

明确告诉用户无需引入专门 Tool / Skill，并给最小可行做法。

### B — 专门方案有明显增益

围绕具体能力缺口做定向发现与比较，默认只保留 1 个主推荐；只有存在明显差异化时才给第 2 个。

能力更强不代表一定值得采用；还必须考虑安装、学习、迁移、企业权限和数据边界。

### C — 暂不值得引入复杂方案

给一个低成本试验方式，说明什么条件出现后再升级。

因此 `0–2` 只是正式资源推荐位的默认数量，不是产品本身。

## 6. 搜索与证据顺序

当用户真正需要外部资源时，默认从**用户怎么学、怎么做、踩什么坑**出发，而不是从厂商功能目录出发。

### 6.1 默认三层证据顺序

对于“这个工作怎么做得更好 / 这个 Skill 值不值得用”这类采用问题，默认按三层组织：

1. **第三方实操 / 测评 / 攻略 / 案例**：优先回答怎么用、实际流程、效果、返工、坑、适用人群；
2. **原始实现 / Skill / Tool / 仓库**：确认具体能力、输入输出和真实交付物；
3. **官方 / 当前原始事实**：只对版本、安装、兼容、价格、隐私、许可证、当前原生能力等易变化事实做兜底核验。

这不是绝对网站排序，而是**用户价值排序**。如果某个原始仓库本身就是最好的实操教程，它可以同时承担第 1、2 层。

### 6.2 第三方实操优先的来源

优先发现真正展示操作过程的来源，包括但不限于：

- Bilibili / YouTube；
- 微信公众号；
- 小红书；
- 知乎、掘金、CSDN、人人都是产品经理等社区；
- AI 产品经理 / 企业咨询 / Agent 实践作者的博客与系列内容；
- GitHub 上已经整理好的 PM / Agent / Skill 资源库、教程库和蓝皮书。

作者、粉丝、收藏、点赞、播放、Stars 只影响**先看谁**，不能替代阅读具体内容。

### 6.3 平台访问边界

必须区分：

```text
平台上有没有高价值内容
!=
当前 Agent 是否能完整读取该内容
```

- 普通 Web 能检索到 B站视频时，先用于发现；需要完整字幕/正文且普通路径拿不到时，再考虑批准过的 Adapter；
- 微信可按需使用已验证的 Search → Reader；
- 小红书若因登录、动态渲染、反爬或索引限制拿不到原文，记录 `Coverage gap`，不能推断“平台没有好内容”；
- 搜索摘要、标题、互动量不能冒充原文证据。

### 6.4 已有生态优先于自建

当互联网上已经存在成熟的：

- PM / BA Skill 库；
- Agent / Codex / WorkBuddy 实战教程；
- 原型、PRD、流程图、PPT、数据处理工作流；
- 社区蓝皮书、教程系列、作者专题；

ERP AI Curator 应把它们作为**上游 feeder ecosystem**，做筛选、核验和 ERP 任务映射，而不是重新写一套同类知识库。

只有现成资源无法满足真实用户问题时，才允许 Curator 补充 `Curator synthesis`；必须显式标注，不能冒充第三方资源。

### 6.5 何时自己实测

不把每个候选都送进本地 runtime / artifact test。

只有当以下至少一项成立时，才值得做最小实测：

- 高价值第三方实操证据明显不足；
- 不同测评之间存在关键冲突；
- 安装、权限、隐私、安全或企业环境风险高；
- 准备把某个可执行 Tool / Skill 作为内部长期标准推荐；
- 当前能力声明会直接决定推荐，但仅靠文档无法确认。

否则，**优质第三方实操 + 原始实现核验 + 必要官方事实**已经足够进入资源推荐。

## 7. 何时触发，何时退出

### 应介入

用户在选择或探索一种可复用的 AI 工作方式，例如：

- “这个工作怎么用 AI 做得更好？”
- “有没有更适合的 AI 方法？”
- “这个事情值得装 Skill 吗？”
- “帮我找一个能做到 X 的 Tool / Skill。”

用户不需要先知道应该搜索什么资源。

即使用户明确说“帮我找 Skill”，Skill 也可以在明显 over-tooling 时告诉用户“当前没必要装”。

### 不抢占

用户只是要求完成一次任务，例如解释业务、改代码、写周报、直接做原型时，不主动转成资源推荐。

核心边界：

> **用户是在执行任务，还是在选择一种 AI 工作方式？**

## 8. 产品成功意味着什么

真正价值不是链接数量，而是让用户：

- 更快判断 AI 是否值得介入；
- 少装错工具、少走过时路径；
- 更快开始实际工作；
- 少花时间在方案选择和学习路径上；
- 在需要专门方案时得到少量高价值选择；
- 在不需要专门方案时被及时劝退；
- 面对真实项目材料时，降低生成结果的返工、校验和格式整理成本。

一次成功运行应该让用户感觉：

> “我现在知道这个任务最合适的 AI 做法，而且可以马上开始。”

对于实操型资源采编，还有一个更严格的检查：

> **“如果今晚把这个资源发给同事，他明天能不能拿真实项目材料开始用，而不是只知道一个新概念？”**

## 9. 当前不做

在真实使用证明必要性之前，不建设：

- 大型资源数据库；
- 固定场景 taxonomy；
- 自动 Refresh 系统；
- 统一评分体系；
- Gate / candidate JSON；
- 复杂 validator；
- 多 Agent 工作流编排；
- 固定搜索次数；
- 影响者/UP主排行榜或封闭白名单；
- 为单一失败案例增加专门规则；
- 为每个候选强制做 runtime / artifact test；
- 重新建设已经存在的 PM Skill 库、WorkBuddy 教程库、Agent 教程库或类似社区生态；
- 因为当前工具读不到某个平台就降低该平台在产品中的价值判断。

## 10. 决策原则

任何新规则、字段、脚本、数据库或自动化进入主线前，先问：

> **删除它以后，泛 ERP 用户选择 AI 工作方式的结果会明显变差吗？**

不能明确回答“会”，默认不加。

任何验证题进入产品证据前，先问：

> **它是真实工作问题，还是我们为了证明自己而设计的问题？**

后者只能作为测试，不能当产品成功证据。

任何准备自己开发/整理的新能力进入主线前，再问：

> **互联网上是否已经有足够好的现成 Skill、教程、作者体系或社区资源可以直接吸收？**

如果答案是“有”，默认先做 Curator，不做 Builder。

### 10.1 目标层级不可倒置

项目执行始终服从：

```text
North Star
→ 当前阶段里程碑
→ 真实用户结果 / 能改变决策的证据
→ 任务
→ 文档 / 测试 / Commit / Tool / Agent
```

下层只能服务上层，不能反过来定义项目进度。

因此：

- “本地 Agent 现在可以做什么”不是立项理由；
- “可以再做一次 smoke / readiness / benchmark”不是立项理由；
- “做完会有一个文档 / PR / PASS”不是产品价值证明；
- 工程资产只有在推进当前里程碑或解除真实阻塞时才值得现在做。

### 10.2 代理目标反事实检查

任何非平凡任务开始前，先问：

> **如果这个任务完美完成，但没有任何真实用户因此更快做出选择、开始工作、减少返工，也没有解除一个真实阻塞，项目是否真的更接近当前目标？**

如果答案是“否”，默认不做。

这条规则优先于“保持 Agent 忙碌”“把系统做完整”“先证明 readiness”等工程冲动。

### 10.3 自测不等于产品证据

Synthetic、smoke、regression、runtime 测试可以验证实现或反驳设计，但不能单独证明产品价值。

真实用户阶段开始后，除非自测用于修复**真实使用暴露的缺陷**或解除**真实 Pilot 的明确阻塞**，否则不得用自测结果替代真实采用反馈，也不得因为自测容易执行就把项目拉回验证阶段。
