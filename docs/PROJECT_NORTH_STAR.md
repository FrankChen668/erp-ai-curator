# ERP AI Curator — Project North Star

## 1. 项目为什么存在

ERP AI Curator 不是“AI 资源搜索器”，也不是“AI 工具大全”。

它面向实施顾问、项目经理、开发人员的真实工作任务，在**用户确实需要找外部资源**时，替用户完成：

`理解任务 → 搜索 → 打开原始内容 → 横向比较 → 淘汰 → 输出少量强资源`

一句话定义：

> **把高噪声互联网资源压缩成少量真正值得 ERP 项目人员投入时间的 Skill / Tool / 教程 / 方法。**

默认输出 0–2 个；没有强匹配时允许 0 个。

## 2. 真正的上游不是“资源”，而是“问题”

项目必须从真实工作问题开始，而不是从已有资源反推使用场景。

有效输入优先级：

1. `REAL_USER`：真实顾问 / PM / 开发人员原始问题（问卷、访谈、实际求助）
2. `OWNER_REAL`：项目负责人自己真实遇到并希望解决的问题
3. `REPRESENTATIVE`：为了覆盖边界而设计的代表性题目
4. `SYNTHETIC`：纯测试构造题

只有前两类可以作为主要产品验证证据；后两类只能做边界测试与回归。

## 3. 三类用户必须覆盖

项目不能只优化实施顾问。

必须覆盖：

- 实施 / 业务顾问：流程、原型、Fit-to-Standard、需求分析、陌生模块学习等
- 项目经理：项目计划、会议与行动项、风险/问题管理、状态汇报、变更影响等
- 开发人员：代码库理解、架构图、接口/影响分析、Agent 配置、测试与调试等

如果真实需求长期集中在某一角色，产品可以收缩，但不能在没有数据前假定“ERP 顾问 = 全部用户”。

## 4. 何时不应该介入

ERP AI Curator 只解决“找什么外部资源值得用”。

以下请求默认不触发：

- 直接解释 SAP / Oracle 业务知识
- 直接写需求、代码、方案
- 直接画流程图或做原型
- 直接做项目计划

除非用户明确问“有没有值得用的 Skill / Tool / 教程来完成它”。

否则 Curator 会退化成一个无所不包的通用 Agent。

## 5. 产品价值不是链接数量

真正价值是：

- 用户少搜很多页面；
- 少踩过时 / 营销 / 错配资源；
- 更快开始实际工作；
- 推荐结果愿意直接分享给同事；
- 稀缺主题敢于明确说“没有找到够格资源”。

`0–2` 是默认输出策略，不是产品目标本身。

## 6. 当前暂不做什么

在真实问题验证之前，不进入：

- 大型资源数据库
- 自动 Refresh 系统
- 统一评分体系
- Gate / candidate JSON
- 复杂 validator
- 多 Agent 流程编排
- 为测试题写专门规则

这些只有在真实使用暴露明确重复成本后才有资格进入主线。

## 7. 决策原则

每当想新增规则、字段、脚本、数据库或自动化时，先问：

> **删除它以后，真实 ERP 用户最终拿到的推荐会明显变差吗？**

不能明确回答“会”，默认不加。

每当想新增一个验证题时，先问：

> **这是用户真实问题，还是我们为了证明自己的方案而设计的问题？**

如果是后者，只能作为测试样本，不能当产品证据。
