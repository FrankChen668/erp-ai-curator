# ERP AI Curator — Project North Star

> Current product contract. Historical detailed analysis model: `docs/AI_LEVERAGE_MODEL_V3.md`.

## 1. 项目为什么存在

ERP AI Curator 面向 **泛 ERP / 企业信息化从业者**，覆盖 SAP / Oracle、二开与集成、定制供应链/财务/采购/制造系统，以及 ERP 周边平台、接口、数据、测试与运维。

目标角色包括实施/业务顾问、项目经理、产品经理、解决方案人员和开发人员。

真正要解决的问题是：

> **面对一个真实企业信息化工作任务，别人已经有哪些值得学习的 AI 实践？当前 AI / 工具链是否已经够用？如果确实存在能力缺口，什么现成能力最值得补？**

因此项目不是 AI 工具大全，也不只是资源搜索器。

## 2. 一句话定义

> **泛 ERP / 企业信息化工作的 AI 工作方式导航器：从真实任务出发，优先吸收互联网上已经存在的实战经验与现成能力，把高噪声资源压缩成少量真正值得学习或采用的选择。**

产品层主链路可以包含两种不同用户意图：

```text
找实践：真实任务 → practitioner discovery → 候选调查 → 少量高匹配实践/教程
做选型：真实任务 + 当前工具链 → 具体能力缺口 → 候选能力核验 → 最小必要升级或明确劝退
```

两种意图可以同时存在，但不应在 Runtime 中被强行混成同一个默认行为。

搜索只是按需动作；重复造教程、重新发明已有工作法、为每个候选做实验室式验证都不是产品目标。

## 3. 上游永远是真实工作问题

项目必须从真实工作问题开始，而不是从已有资源反推使用场景。

有效输入优先级：

1. `REAL_USER`：真实从业者原始问题（问卷、访谈、实际求助）
2. `OWNER_REAL`：项目负责人自己真实遇到的问题
3. `REPRESENTATIVE`：为了覆盖边界而设计的代表性题目
4. `SYNTHETIC`：纯测试构造题

前两类用于产品证据；后两类只用于边界测试和回归。

不把真实问题先改写成“适合 Skill 的标准场景”。

需要归一化真实问题用于搜索和验证时，优先保留：

```text
真实情境
+ 手头已有项目材料
+ 当前必须完成的动作
+ 下一份明确交付物
+ 时间 / 评审 / 数据边界
```

Problem Card 只是保存真实任务结构，不是永久场景 taxonomy。

## 4. 一个产品，两种 Runtime 职责

不为 SAP、Oracle、供应链、财务、项目管理、开发分别建设固定 Skill；按**用户决策职责**拆分 Runtime。

### 4.1 Practice Curator — 找别人已经怎么做

`skills/curating-erp-ai-resources/`

负责：

- 最佳实践；
- 教程/案例；
- practitioner workflow；
- 值得优先学习的外部资源。

核心是**搜索、筛选、调查和压缩**，不是自己写一篇教程，也不是默认推荐安装 Tool/Skill。

### 4.2 Capability Advisor — 判断是否需要新增能力

`skills/advising-erp-ai-capabilities/`

负责：

- 当前 AI / 工具链是否已经够用；
- 是否存在具体能力缺口；
- 是否值得新增 Tool / Skill / MCP / plugin / Agent / workflow；
- 如果值得，最小必要升级是什么。

核心是**能力缺口与采用成本判断**，不是 Skill 商店导购。

### 4.3 为什么拆 Runtime

真实受控使用反复出现同一种串台：用户只问“最佳实践”，Agent 却被 Tool/Skill/MCP 语义吸引，最终退化成 Skill 搜索和安装建议。

Agent Skills 的 `description` 是主要触发机制。两个职责使用互斥描述，比继续在同一个 Skill body 里增加 guardrail 更能降低触发和执行污染。

这是 Runtime 单一职责拆分，不是产品拆分，也不增加 Router Skill。

## 5. 能力选型的合法结果

以下仅属于 `advising-erp-ai-capabilities` 的采用判断，不要求 Practice Curator 先做分类：

### 现有工具已够

不存在值得采用成本的具体能力缺口。明确劝退新增能力并停止。

### 值得补能力

围绕具体缺口做定向发现与核验，默认只保留 1 个主推荐；只有存在明显不同的采用边界时才给第 2 个。

### 条件式升级

当前是否升级取决于一个真实未知条件，例如系统访问、格式、规模、权限、隐私或重复频率。明确条件，不制造确定性。

历史 A/B/C 标签可继续存在于历史分析证据中，但不作为当前 Runtime contract。

## 6. 搜索与证据顺序

当用户真正需要外部资源时，默认从**用户怎么学、怎么做、踩什么坑**出发，而不是从厂商功能目录出发。

### 6.1 实践策展

优先：

1. **第三方实操 / 测评 / 攻略 / 案例**：实际流程、输入输出、返工、坑、适用人群；
2. **原始实现 / repo / workflow**：确认实践到底使用或产出什么；
3. **官方 / 当前原始事实**：只核验版本、兼容、标准语义等会改变理解的当前事实。

中文 ERP / ToB / 产品/项目语境可优先发现：

- Bilibili / YouTube；
- 微信公众号；
- 小红书；
- 知乎、掘金、CSDN、人人都是产品经理；
- AI 产品经理 / 企业咨询 / Agent 实践作者；
- 相关 GitHub 教程、案例和工作流。

作者、粉丝、收藏、点赞、播放、Stars 只影响**先看谁**，不能替代阅读具体内容。

### 6.2 能力选型

只有先确认具体能力缺口后，才定向核验 Tool / Skill / MCP / plugin / Agent / workflow。

优先确认：

- 输入/输出和真实交付物；
- 当前维护和兼容；
- 安装/账号/依赖；
- 权限、数据外发、写操作；
- 学习/迁移/维护成本；
- 必要时的独立 practitioner 采用或失败经验。

“找到一个 Skill”本身不是推荐理由。

### 6.3 平台访问边界

必须区分：

```text
平台上有没有高价值内容
!=
当前 Agent 是否能完整读取该内容
```

- 普通 Web 能发现 B站等内容时先用于 discovery；
- 需要完整正文/字幕且普通路径拿不到时，记录 `coverage/policy gap`；
- 只有已批准的 read-only adapter 能实质补足重要证据时才按需使用；
- 搜索摘要、标题和互动量不能冒充原文证据。

### 6.4 已有生态优先于自建

当互联网上已有成熟 Skill、教程、作者体系、社区资源或工作流时，默认先做 Curator，不做 Builder。

只有现成资源无法满足真实问题时，才补充 `Curator synthesis`；必须显式标注，不能冒充第三方实践。

### 6.5 何时自己实测

不把每个候选送进本地 runtime / artifact test。

只有当测试结果可能改变推荐，例如：

- 高价值第三方实操证据明显不足；
- 测评存在关键冲突；
- 安装、权限、隐私、安全或企业环境风险高；
- 准备把某个可执行能力作为内部长期标准；
- 核心能力声明仅靠文档无法确认。

否则，优质实操 + 原始实现核验 + 必要官方事实已经足够。

## 7. Runtime 触发边界

### Practice Curator

典型请求：

- “给我找下做流程图的最佳实践。”
- “有没有产品经理/ToB 用 AI 做原型的实操教程？”
- “别人怎么用 AI 维护 ERP 操作手册？”

这类请求默认**不进入 Tool/Skill 安装选型**。

### Capability Advisor

典型请求：

- “我现在 ChatGPT + draw.io 已经够了吗？”
- “这个事情值得装 Skill 吗？”
- “这几个 Tool/Skill/MCP 哪个更适合？”
- “我要不要给 Agent 接 SAP/数据库只读访问？”

这类请求先确认具体能力缺口，再决定是否搜索新能力。

### 两者同时存在

例如：

> “先帮我找流程图最佳实践，再看看有没有必要装新的 Skill。”

可以同时使用两个 Runtime Skill，各自完成自己的职责；不要为此新增第三个 Router Skill。

### 不抢占

用户只是要求完成一次任务，例如解释业务、改代码、写周报、直接做原型时，不主动转成资源推荐或能力选型。

## 8. 产品成功意味着什么

真正价值不是链接数量，而是让用户：

- 更快找到真正值得学的实践；
- 少装错工具、少走过时路径；
- 更快开始实际工作；
- 少花时间在搜索、筛选和方案选择上；
- 在需要专门方案时得到少量高价值选择；
- 在不需要专门方案时被及时劝退；
- 面对真实项目材料时，降低返工、校验和格式整理成本。

一次成功运行应该让用户感觉：

> “我现在知道这个任务值得先学什么、要不要补新能力，而且可以马上开始。”

对于实操型资源，还有一个更严格的检查：

> **“如果今晚把这个资源发给同事，他明天能不能拿真实项目材料开始用，而不是只知道一个新概念？”**

## 9. 当前不做

在真实使用证明必要性之前，不建设：

- 大型资源数据库；
- 固定场景 taxonomy；
- 自动 Refresh 系统；
- 统一评分体系；
- Gate / candidate JSON；
- 复杂 validator；
- 第三个 Router Skill；
- 多 Agent 工作流编排；
- 固定搜索次数；
- 影响者/UP主排行榜或封闭白名单；
- 为单一失败案例增加场景专用规则；
- 为每个候选强制 runtime / artifact test；
- 重新建设已经存在的 PM Skill 库、Agent 教程库或类似社区生态；
- 因为当前工具读不到某个平台就降低该平台在产品中的价值判断。

## 10. 决策原则

任何新规则、字段、脚本、数据库或自动化进入主线前，先问：

> **删除它以后，泛 ERP 用户找到正确实践或做出正确能力选择的结果会明显变差吗？**

不能明确回答“会”，默认不加。

任何验证题进入产品证据前，先问：

> **它是真实工作问题，还是我们为了证明自己而设计的问题？**

后者只能作为测试，不能当产品成功证据。

任何准备自己开发/整理的新能力进入主线前，再问：

> **互联网上是否已经有足够好的现成 Skill、教程、作者体系或社区资源可以直接吸收？**

如果答案是“有”，默认先做 Curator，不做 Builder。

### 10.1 目标层级不可倒置

项目执行始终服从：

```text
North Star
→ 当前阶段里程碑
→ 真实用户结果 / 能改变决策的证据
→ 任务
→ 文档 / 测试 / Commit / Tool / Agent
```

下层只能服务上层，不能反过来定义项目进度。

因此：

- “本地 Agent 现在可以做什么”不是立项理由；
- “可以再做一次 smoke / readiness / benchmark”不是立项理由；
- “做完会有一个文档 / PR / PASS”不是产品价值证明；
- 工程资产只有在推进当前里程碑或解除真实阻塞时才值得现在做。

### 10.2 代理目标反事实检查

任何非平凡任务开始前，先问：

> **如果这个任务完美完成，但没有任何真实用户因此更快找到实践、做出选择、开始工作、减少返工，也没有解除真实阻塞，项目是否真的更接近当前目标？**

如果答案是“否”，默认不做。

### 10.3 自测不等于产品证据

Synthetic、smoke、regression、runtime 测试可以验证实现或反驳设计，但不能单独证明产品价值。

真实用户阶段开始后，除非自测用于修复**真实使用暴露的缺陷**或解除**真实 Pilot 的明确阻塞**，否则不得用自测结果替代真实采用反馈。
