# User Journeys & Product Contract

## 1. 默认输入

用户通常只需要给一个自然语言任务，例如：

- “帮我找适合顾问画业务流程图的 AI Skill 和教程。”
- “Claude Code 接便宜第三方模型，有没有当前还靠谱的配置方法？”
- “SAP 顾问怎么用 AI 做 Fit-to-Standard？”
- “我对 Oracle 某模块不熟，找一些能快速入门的 AI 实战资源。”

可选约束：

- 角色：实施顾问 / PM / 开发；
- 平台：SAP / Oracle / 通用；
- 资源类型：Skill / Tool / 教程 / 视频 / 官方文档 / 案例；
- 语言：中文优先 / 英文可接受；
- 环境：Claude Code / Codex / WorkBuddy / TRAE 等；
- 时效：必须当前可用。

如果这些约束没有明确给出，Skill 应根据任务做合理推断，不要为了补字段而阻塞用户。

## 2. 默认运行逻辑

### Step 1 — 理解真实任务

先回答三个问题：

- 谁要用？
- 要完成什么动作？
- 最终希望得到什么可用结果？

例如“AI 流程图”不能只按关键词搜索；要判断用户要的是：

- 可编辑业务流程图；
- BPM 工作流系统配置；
- Mermaid 代码；
- 架构图；
- 还是只要展示图。

### Step 2 — 多角度发现候选

搜索目标不是“达到固定数量”，而是覆盖有竞争力的不同来源。

优先考虑：

- 原始 GitHub / Skill 仓库；
- 官方教程或产品文档；
- 有明确步骤和产出的中文教程；
- 高质量英文实操资源；
- 真实项目案例。

搜索应主动变化关键词和来源，避免只重复同一批转载结果。

### Step 3 — 阅读原始内容

推荐前必须实际理解候选主要内容，不能只根据：

- 搜索摘要；
- 标题；
- Star 数；
- 点赞数；
- AI 摘要。

### Step 4 — 横向比较

默认比较以下问题：

1. 是否直接解决当前任务？
2. 用户照着它能得到什么？
3. 是否有步骤、示例、结果或真实实现？
4. 当前是否仍可用？
5. 相比其他候选，它为什么更值得用户花时间？
6. 有什么重要限制？

这里需要模型判断，不要求把每项变成固定分数。

### Step 5 — 风险触发式事实核验

如果候选涉及高时效、高失败成本的事实，再查当前官方/原始来源。

典型触发：

- “设置这个环境变量就能运行”；
- “支持某模型/版本”；
- “这个产品原生可以完成某配置”；
- “价格只有多少”；
- “使用某 API endpoint”。

普通方法论和案例不默认进入重型 Claim Verification。

### Step 6 — 做决定

默认输出 0–2 个最终推荐。

不是“把所有不错的都列出来”，而是让最强候选彼此竞争。

如果没有强匹配：明确返回 0 推荐。

## 3. 默认输出契约

优先使用紧凑表格：

| 资源 | 类型 | 为什么值得看 | 适合得到什么 | 重要限制 |
|---|---|---|---|---|
| 原始标题 + 原始链接 | Skill / Tool / 教程 / 官方文档 / Case | 1 句话 | 1 句话 | 必要时填写 |

规则：

- 默认最多 2 个；
- 必须给原始链接；
- 推荐理由必须说明具体可用价值；
- 不写“最好、最强、必看”等空泛结论；
- 不重写整篇教程；
- 不展示内部评分、Gate、Candidate JSON；
- 必要时增加一行“为什么没有推荐更多”。

### 0 推荐输出

示例结构：

> 这轮没有找到我认为值得直接推荐的资源。最接近的候选主要问题是：内容过时 / 只有营销介绍 / 输出物与任务不符。建议保留空缺，不凑数。

不需要输出完整淘汰清单，除非操作者明确要求审计过程。

## 4. 五个核心用户旅程

### Journey A — 找一个能直接用的 Skill / Tool

输入：

> “找一个能让 Claude Code 画可编辑 draw.io 流程图的 Skill。”

成功结果：

- 类型匹配；
- 仓库真实、当前可用；
- 明确安装/前置；
- 明确最终能产出什么。

如果用户明确说“只要 Skill”，Tool 不得冒充 Skill。

### Journey B — 找一篇实操教程

输入：

> “找一篇中文教程，教我用 AI 做原型。”

成功结果：

- 有实际步骤；
- 有可判断产出；
- 不是只有效果展示；
- 中文质量足够好。

若中文明显没有够格资源，可以推荐更强英文资源，但必须说明原因。

### Journey C — 查配置/兼容性

输入：

> “Claude Code 接 OpenRouter 现在怎么配？”

成功结果：

- 优先当前官方配置；
- 关键变量、endpoint、版本范围经过核验；
- 第三方教程与官方冲突时不推荐第三方。

这是强事实核验路径。

### Journey D — 找 ERP 方法/案例

输入：

> “SAP 项目需求调研和 Fit-to-Standard，有什么 AI 实战案例？”

成功结果：

- 必须真正进入需求调研 / Fit-Gap / Fit-to-Standard 工作；
- AI use-case ideation、泛数字化 Workshop 不因为“SAP 官方”就占位；
- Vendor 案例可推荐，但来源自述指标应明确是厂商声称。

### Journey E — 找不到好资源

输入：

> “Oracle 陌生模块学习，有没有高质量 AI Prompt Framework？”

如果没有强候选：

- 保持空缺；
- 不拿 SAP 泛化；
- 不拿普通 Prompt 列表凑数；
- 可简要指出搜索方向仍缺什么。

## 5. 产品边界

### 产品必须做

- 理解任务；
- 搜索多个来源；
- 打开原始内容；
- 横向比较；
- 做明确选择；
- 必要时做当前事实核验；
- 输出可直接分享的少量链接。

### 产品默认不做

- 不建设完整互联网资源索引；
- 不把资源全部存库；
- 不长期维护每个候选生命周期；
- 不执行候选仓库中的脚本或安装命令作为验证；
- 不绕过登录、付费墙、验证码；
- 不替原作者生成“改写版教程”；
- 不用固定评分代替判断；
- 不把官方文档自动视为推荐；
- 不保证每题都有结果。

## 6. 降级行为

如果当前 Agent 没有 Web 搜索或无法打开原始资源：

- 不应假装完成当前资源采编；
- 可以说明当前只能基于已有信息给方向，不能完成“当前资源推荐”；
- 不从训练记忆中猜最新链接或配置。

如果某个来源无法访问：

- 继续比较其他可验证来源；
- 只有元数据的候选不应被包装成已阅读实操资源。

## 7. 与未来资源库的关系

每次运行产出的“已推荐资源”未来可以成为资源库输入，但这是**输出的后续用途**，不是当前 Skill 必须承担的数据治理职责。

先证明单次推荐质量，再决定是否持久化、Refresh、去重和批量维护。
