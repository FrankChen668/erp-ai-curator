# ERP AI Curator — AI Leverage Model V3

> Status: current product working model. This document supersedes the older assumption that the product only activates when a user explicitly asks for external resources.

## 1. 第一性问题

目标用户不是“SAP / Oracle 产品顾问”，而是更广义的 **泛 ERP / 企业信息化从业者**：

- SAP / Oracle 等标准 ERP 实施与二开；
- Java / .NET 等技术栈建设的定制供应链、财务、采购、制造、主数据等系统；
- 系统集成、接口、数据、测试与运维；
- 实施顾问、业务顾问、项目经理、产品经理、解决方案人员、开发人员。

他们真正缺少的通常不是“搜索结果”，而是：

> **面对一个真实工作任务，我是否值得引入一种更好的 AI 工作方式？如果值得，现成的 Skill / Tool / 方法 / 教程里，哪个最适合我现在使用？**

因此产品的核心问题不是 Resource Search，而是 **AI Leverage Discovery + Decision**。

## 2. 一句话定义

> **面向泛 ERP / 企业信息化工作的 AI 工作方式导航器：从真实任务出发，先判断用户现有 AI + 现有工具链是否已经够用，再在确有能力缺口时寻找并筛选最值得采用的现成方法、Skill、Tool 或实战资源。**

资源是答案的一种形式，不是产品起点。

## 3. Skill 应该什么时候介入

### 应介入

用户表达的是“如何更好地用 AI 完成工作”，即使没有主动说“帮我找资源”：

- “这个需求分析工作怎么用 AI 做得更好？”
- “我想快速看懂这个 Java 供应链系统，有没有合适的 AI 方法？”
- “我临时接手一个陌生财务模块，AI 怎么辅助我建立整体认识？”
- “有没有更适合顾问快速做原型的做法？”
- “这个事情值得装一个 Skill 吗，还是现有工具就够？”

也应介入明确的资源发现请求：

- “帮我找一个能生成 editable draw.io 的 Skill。”
- “现在 Codex 接第三方模型哪个方案靠谱？”

但用户明确说“找 Skill”只是 solution hypothesis。若新增 Skill 相比现有工具链没有清晰增量价值，仍可回答“不需要额外安装”。

### 不应抢占

用户只是在要求直接完成一次任务时，不主动转成资源推荐：

- “帮我解释这段业务逻辑。”
- “帮我改这段代码。”
- “帮我写项目周报。”
- “根据这些需求直接做一个原型。”

除非用户进一步问“有没有更好的 AI 工作方式 / Tool / Skill”。

边界不是“是否出现 Skill/Tool 关键词”，而是：

> **用户是在执行当前任务，还是在选择一种可复用的 AI 工作方式？**

## 4. 核心工作机制

### Step 1 — 理解真实工作任务和当前 baseline

先搞清楚：

- 用户最终想交付什么；
- 当前工作对象是什么（标准 ERP、二开、定制系统、代码库、项目材料等）；
- 用户已经有什么 AI / Agent / 内部工具 / exporter / workflow；
- 有什么关键限制（可编辑、本地运行、数据保密、源码边界、版本、权限、成本等）；
- 当前痛点在哪里。

不需要先把任务塞进固定场景分类。

### Step 2 — 诊断 AI 杠杆点

判断三件事：

1. **用户现有 AI + 现有工具链已经够不够？**
2. **是否存在一个当前 baseline 无法很好提供的专门能力，能明显降低时间、错误或学习成本？**
3. **用户真正缺的是工具、方法、知识来源、系统访问，还是工作流？**

这一步是 Skill 的核心判断能力。

### Step 3 — 选择工作模式

#### Mode A：当前工具链已经足够

不要为了推荐资源而搜索。

直接告诉用户：当前任务没有必要新增专门 Skill / Tool，并给一个最小可行的使用方式。

对于 ERP 业务、配置、代码、接口等专业知识，Mode A 也应尽量采用 source-grounded analysis：围绕用户材料、项目文档、代码、配置或可信知识源工作，而不是只依赖模型记忆。

#### Mode B：专门 AI 工作方式有明显增益

明确“需要补的能力是什么”，然后只围绕这个能力缺口做定向发现。

例如：

- 需要 editable diagram，而不是“找流程图资源”；
- 需要 codebase static map，而不是“找架构工具”；
- 需要 runtime tracing，而不是“找 Agent Graph”；
- 需要 workshop transcript → requirement，而不是“找 AI 需求分析文章”。

专门方案除了能力更强，还必须值得其安装、学习、迁移、账号/权限和数据边界成本。

#### Mode C：是否值得引入专门方案尚不确定

优先给一个低成本试验方式，而不是先建设复杂工具链。

Mode C 必须包含一个具体最小试验和一个 upgrade signal。

## 5. 搜索不是主流程，搜索是按需动作

只有 Mode B 需要外部发现时才搜索。

搜索原则：

- **决策驱动，不是穷举驱动**；
- 先形成“需要什么能力”的假设，再搜索；
- GitHub、社区实战、教程、视频、官方材料都可以成为来源；
- 不设“官网天然优先推荐”；
- 官方主要用于高风险动态事实核验，或官方材料本身就是最佳实操资源时；
- 找到足以稳定做出选择的候选后停止，不为了覆盖率继续扩张。

禁止把“搜了多少站点 / 打开多少官网页面”当成果。

## 6. 候选如何判断

重点只看：

1. 是否解决完整任务，而不是只匹配关键词；
2. 用户实际能得到什么结果；
3. 是否比用户当前 AI + 当前工具链明显更值得采用；
4. 是否有可执行路径，而不是概念宣传；
5. 安装、学习、迁移、权限和企业数据边界是否可接受；
6. 当前是否仍可用；
7. 什么情况下不要用它。

如果第 3 条说不清，默认不推荐新增专门方案。

只有安装、配置、API、Endpoint、环境变量、模型兼容、价格、版本、标准产品原生能力等高波动事实，才升级做强官方核验。

## 7. 输出不再强制等于“资源表”

### Mode A 输出

> 不需要新增专门 Skill / Tool。现有 AI / 工具链已足够，建议这样做：……

### Mode B 输出

默认只给 1 个主推荐，确有明显差异化时给第 2 个：

- **推荐什么**
- **为什么适合当前任务**
- **相比现有工具链多了什么价值**
- **能得到什么**
- **怎么开始**
- **重要限制**
- 原始链接

### Mode C 输出

> 目前不值得先装复杂方案。建议先做这个低成本试验；如果出现 X，再升级到专门工具。

`0–2` 只约束正式资源推荐位，不是整个产品的固定输出格式。

## 8. 不建立场景百科

不要提前为“财务 / 供应链 / 项目管理 / 开发 / SAP / Oracle”分别堆规则和资源。

这些只是用户任务的背景，不是 Skill 的运行逻辑。

同一个工作机制应该能处理：

- SAP 标准实施；
- Oracle Fusion；
- Oracle / SAP 二开；
- Java 定制供应链系统；
- 自研财务系统；
- ERP 周边集成与开发。

Skill 的泛化来自“任务理解 + AI 杠杆判断”，不是来自场景枚举。

## 9. 历史资源怎么用

过去已经发现的高质量资源只作为：

- 搜索先验；
- 候选缓存；
- 已知能力线索。

它们不是固定答案，也不能阻止运行时发现更好的新方案。

高波动资源必须重新核验当前状态。

## 10. 成功标准

一次成功运行的感觉应该是：

> “我本来不知道这个工作是否值得引入新的 AI 方法，现在我知道现有工具够不够、缺什么能力，以及下一步最合适怎么做。”

而不仅仅是：

> “我少搜了几个网页。”

真正要减少的是：

- 试错成本；
- 方案选择成本；
- 学习路径成本；
- 重复建设成本；
- 过时工具与错配工具带来的浪费。

## 11. 对后续 Skill 实现的约束

未来如果重新实现 Skill，主文件只需要表达：

`理解任务与当前 baseline → 诊断 AI 杠杆 → 选择 Mode A/B/C → 必要时定向发现 → 比较 → 按需核验 → 给出可执行建议`

第一版仍默认：

- 不建数据库；
- 不建统一评分；
- 不建 Gate；
- 不建候选 JSON；
- 不建固定场景 taxonomy；
- 不设固定搜索次数；
- 不用脚本替代“是否值得采用”的判断。

任何新增机制都必须回答：

> **它是否让泛 ERP 用户更快选到更好的 AI 工作方式？**

如果不能明确回答“是”，不进入主线。
