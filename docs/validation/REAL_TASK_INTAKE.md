# Real Task Intake — 真实问题进入项目的最小闭环

## 1. 目的

ERP AI Curator 的上游必须是真实工作问题，而不是资源分类或测试题。

现阶段最重要的输入渠道是内部 AI 培训问卷、访谈、实际求助和项目工作中已经发生的问题。

原则：**保留原始问题，先判断是否真的需要找外部资源，再决定是否进入 Curator。**

## 2. 可接受来源

优先级：

1. `REAL_USER`：实施顾问 / 项目经理 / 开发人员真实提交的问题；
2. `OWNER_REAL`：项目负责人自己真实遇到的问题；
3. `REPRESENTATIVE`：为了边界覆盖设计的问题，只做测试；
4. `SYNTHETIC`：纯构造题，只做回归。

产品价值判断主要看前两类。

## 3. 最小记录字段

每个问题只记录：

```text
Task ID
Source
Role（已知才填）
Original problem（原文，不润色）
Context / attachment（有则保留）
Need external resource? yes / no / uncertain
Curator action（仅 yes 时）
Owner judgement
Observed use（有则记录）
```

不建立复杂表单、统一评分或 candidate JSON。

## 4. 问卷如何进入

培训问卷的开放题应优先收集“真实工作卡点”，例如：

- 最近一次你希望 AI 帮你解决、但没有解决好的具体问题是什么？
- 如果有对应文档 / 截图 / 输入样例，可附上；
- 你希望最终得到什么可用结果？

收到回答后：

1. 原文保存；
2. 标记角色；
3. 不先改写成“适合 AI 的标准问题”；
4. 先判断用户需要的是直接答案 / 执行，还是需要找 Skill / Tool / 教程；
5. 只有后者进入 Curator 搜索；
6. 结果返回后记录是否愿意分享 / 实际尝试。

## 5. Triage：Curator 要不要介入

### 直接退出

例如：

- “帮我解释 SAP SD 定价过程”
- “帮我写项目周报”
- “帮我分析这段 ABAP”

这些更适合直接由 AI 完成，不应该为了 Curator 而强行找资源。

### 应进入 Curator

例如：

- “有没有能把需求直接做成交互原型的 Skill？”
- “现在 Claude Code 接第三方模型，哪个方案靠谱？”
- “有没有适合 SAP 顾问做 Fit-to-Standard 的 AI 方法？”

这里用户真正需要的是“找什么值得用”。

### 不确定

若同一个问题既可直接完成、也可能需要工具，例如“我想长期自动整理会议纪要和行动项”，先判断用户是在求一次性结果还是在选长期工作方式。

## 6. 问题池不是资源目录

问题池按真实工作任务保存，不按 Tool / Skill / Tutorial 分类。

错误方式：

> 收集 20 个 Skill 主题，再给每个主题补用户故事。

正确方式：

> 收集真实卡点，再判断哪些卡点需要外部资源。

## 7. 去重规则

只做语义聚类，不覆盖原文。

例如多个问题都在问“陌生模块快速学习”，可以归到一个主题，但仍保留每条原始问题和角色差异。

聚类用于发现重复需求，不用于把用户问题改造成统一 Prompt。

## 8. 什么时候形成产品机制

只有当真实问题反复出现后，才考虑：

- 固定检索策略；
- Starter Pack；
- Skill trigger；
- 持久化资源；
- 自动刷新。

不要为了“系统完整”提前建设。

## 9. 当前执行方式

云端负责：

- 收集并整理已知真实问题；
- 搜索与阅读原始来源；
- 形成 0–2 推荐；
- 记录关键限制；
- 更新 GitHub。

本地 Agent 不进入这个判断链路。
