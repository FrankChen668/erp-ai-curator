# ERP AI Curator — 项目重新盘点（2026-08-29）

## 1. 结论先行

项目**不需要推倒重来**。Phase 1–3 的产品判断大体成立，真正失败的是 Phase 4 的执行路径：我们过早把“证明产品价值”转换成了“让本地 Agent 实现 Skill + 运行 A/B 测试”。

新的核心原则：

> **先证明“资源选择方法”本身稳定有价值，再把它固化成 Skill。**

因此暂停本地 Agent 作为关键路径，暂停继续修 PR #4，不继续追加 Round 4 / Gate / Script / Validator。

## 2. 哪些结论保留

### 保留 A：产品问题定义

仍采用 Phase 2 的一句话定义：

> 给定一个 ERP 项目中的真实工作任务，从互联网中筛出 0–2 个当前最值得继续投入时间的原始资源，并说明为什么值得看。

价值不是“搜到更多”，而是替用户完成：

`理解任务 → 搜索 → 阅读原文 → 比较 → 淘汰 → 推荐少量强资源`

### 保留 B：0 推荐合法

没有真正匹配的资源时，应明确说没有。

同时防止另一种失败：为了显得谨慎而过度 abstain。

### 保留 C：高判断任务不能做成低自由度 Gate 流水线

V0.2–V0.4 已证明：统一评分、candidate JSON、G0–G5、复杂 validator 很容易优化“规则通过”，而不是优化“是否值得分享”。

### 保留 D：风险触发式事实核验

只对高失败成本事实加强核验：

- 安装 / 配置
- API / endpoint / 环境变量
- 模型兼容
- 价格 / 版本
- 标准产品能力边界

普通方法、案例、教程不默认进入重型 Claim Audit。

### 保留 E：Progressive Disclosure

主 Skill 只应描述主路线；搜索策略、选择启发式、高风险核验作为按需 reference。

但这属于**后续 Skill 实现形式**，不是当前产品验证的前提。

## 3. Phase 4 实际证明了什么

### 正向证据

1. E03 表明：高风险事实核验确实能减少过时配置和错误变量。
2. E01 表明：强制横向取舍可以明显减少链接堆积。
3. E08 暴露了“满足局部条件但违背完整任务意图”的真实模型失败，这个问题值得保留为产品启发式。
4. 轻量 Skill 架构没有重新滑向 scripts / Gate / database，这是正确的。

### 不能当作有效结论的部分

1. Baseline / with-skill 的推荐数量不能作为核心指标；Agent 本身具有明显随机性。
2. Round 1 因提前读取全部 references，不能作为严格 progressive-disclosure 证据。
3. Round 2 虽修正测试协议，但又暴露语义钻空子问题。
4. 本地 Agent 多次出现：调用成功≠产物成功、未验收文件、429 后机械重试、把既定决策重新抛给 Product Owner。

所以 Phase 4 最大的工程结论不是“Skill 失败”，而是：

> **当前本地 Agent 不适合作为产品判断和 Eval 可信性的主要负责人。**

## 4. 当前最危险的误区

### 误区 1：继续修 Eval，直到三题都 PASS

这会导致 test overfitting。每发现一个失败就补一条 heuristic，最后又回到 V0.4。

### 误区 2：继续比较 baseline 推荐数

数量收敛不是最终价值。2 个垃圾资源仍然是失败。

### 误区 3：把 A/B 当成第一性验证

我们首先需要验证的是：

> 用户看到推荐结果后，是否真的愿意分享 / 点击 / 使用？

不是先证明 Skill 相比无 Skill 在统计上赢多少。

### 误区 4：继续让本地 Agent 自主管理测试流程

产品判断、证据质量和测试协议应该由云端控制；本地 Agent 以后只承担可机械验收的仓库操作。

## 5. 新的产品验证单位

不再以“一个 Eval Case 是否机械 PASS”为主单位。

改成真实任务 Review Card：

| 字段 | 含义 |
|---|---|
| 真实任务 | ERP 顾问实际会问的问题 |
| 最终推荐 | 0–2 个 |
| 为什么选 | 具体任务价值 |
| 为什么没选其它 | 只记录最关键淘汰原因 |
| 高风险事实核验 | 仅命中时记录 |
| Product Owner 判断 | 值得分享 / 一般 / 不值得分享 |
| 失败原因 | 任务理解 / 搜索覆盖 / 选择错误 / 时效事实 / 过度 abstain |

北极星仍然是：

> **“这 1–2 个链接，我愿不愿意直接发给同事？”**

## 6. 对现有资产的处理

### Main 中 Phase 1–3

保留。它们是有效的设计研究和决策历史。

### 旧 V0.4 Skill

继续冻结，仅作为历史失败样本。

### PR #4 / `impl/phase-04-minimal-skill`

不合并。保留为 Pilot 证据和失败样本，但不继续修补。

其中可复用的知识只有：

- 轻量 SKILL.md 结构；
- source strategy；
- selection heuristics 中经过真实失败暴露的少数原则；
- volatile fact check。

是否最终进入正式 Skill，要等云端真实任务验证后再决定。

## 7. 新阶段定义

下一阶段不叫 Phase 4 Round N。

定义为：

> **Cloud Product Validation — 先验证产品，再实现 Skill。**

由云端直接完成真实搜索、原文阅读、比较和推荐；GitHub 只记录结果和结论。
