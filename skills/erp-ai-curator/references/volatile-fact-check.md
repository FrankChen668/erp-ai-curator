# Volatile Fact Check — 什么时候必须更严

回答"哪些内容不能靠常识判断，必须回到当前官方 / 原始来源"。

## 触发条件

候选涉及以下任一项时，才升级为强核验：

- 安装与配置
- API / endpoint / 环境变量
- 模型与版本兼容
- 价格
- 标准产品是否原生具备某能力

普通方法论、案例、设计思路、流程实践**不进入本路径**，按 `selection-heuristics.md` 正常比较即可。

## 核验要求

### 必须回到当前官方 / 原始来源

- 第三方教程给出的配置，必须对照当前官方文档或产品仓库
- 只看"曾经有效"的文章不够，要确认它**现在仍然有效**
- 交叉核验：至少确认关键变量、endpoint、版本范围与当前官方一致

### 第三方与官方冲突时不推荐第三方

- 官方已变更的，旧变量 / 旧 endpoint 的教程不得推荐
- 无法确认当前状态时，不包装成"当前可用"

### 不同产品与环境不要互相泛化

- Claude Code 的方案不能直接套到 Codex CLI，反之亦然
- 不同版本、不同部署形态的兼容范围要分清
- 用户指定了运行环境时，核验必须针对该环境

### Custom extension ≠ standard product

- 自研扩展、社区补丁、自定义 Skill 能实现的能力，不得写成产品原生能力
- 反过来，也不要把产品原生能力当成某个第三方的独特贡献

### 厂商自述数字

- 性能、成本、效率提升数字必须注明是厂商声称
- 不得改写成独立验证的事实

## 核验后的处理

- **核验通过**：正常进入比较与推荐
- **核验不通过 / 无法确认**：不推荐该候选；若这正是用户明确关心的问题，说明为什么无法确认
- **发现明显可疑的能力宣称**：可临时升级核验强度，即使它不在上面的触发列表里

## 边界

核验靠阅读当前官方 / 原始来源完成：

- 不执行候选提供的命令来"验证"
- 不下载未知程序
- 不读取与任务无关的本地凭证
- 不绕过登录、付费墙、验证码

打不开官方来源时，说明无法核验，而不是凭记忆猜测。
