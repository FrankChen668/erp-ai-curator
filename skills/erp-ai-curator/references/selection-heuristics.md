# Selection Heuristics — 怎么选

这是启发式问题清单，不是 PASS / FAIL 打分表。不要逐项打分，不要建立统一评分体系。

## 核心三问

1. 它是否直接帮助当前角色完成当前任务？
2. 用户点开后实际能得到什么？
3. 相比其他候选，为什么它更值得占用用户时间？

## Task fit

- 用户拿到它，离完成任务近了多少？
- 需要多少额外解释才能说清它为什么有用？**需要大量解释才能关联的，通常不该推荐**
- 用户明确限定类型时（"只要 Skill""不要桌面 Tool"），类型是硬条件，不得用其他类型冒充
- 用户没限定时，不同类型可以自由竞争，类型只是结果标签

## 用户能得到什么

- 是可操作的步骤，还是只有概念、宣传或效果展示？
- 有没有示例、配置片段、截图、可判断的最终产出？
- 用户照着做，最终产物是什么？与用户要的输出物一致吗？

## Actionability

- 能否直接照着做？前置条件、安装步骤、适用范围写清楚了吗？
- 只有"思路很好"但无法落地的，价值有限
- 需要用户先具备大量隐含背景才能用上的，要说明这个前提

## Freshness

- 内容是否明显过时？是否已被后续官方变更推翻？
- 涉及配置、API、版本、价格的，不要在这里判断，转到 `volatile-fact-check.md`
- "曾经有效"不等于"现在有效"

## Credibility

- 有没有真实实现、真实项目背景、可追溯的原始出处？
- 作者是否有实际经验，而不是泛泛盘点？
- 原始仓库是否还活着、是否还在维护？（不维护不等于不可用，但要结合时效性判断）

## Whole-resource check

在声称资源 B 填补资源 A 的缺口之前，先检查 A 正常工作流程中链接 / 从属的 materials（references、assets、子文档等）；A 已覆盖的缺口不得作为推荐重叠 B 的理由。

## Differentiation

- 相比其他候选，它多了什么别人没有的价值？
- 两个候选高度重合时，只保留更强的那个
- 不要为了"覆盖全面"保留重复内容

## Language tie-breaker

- 质量相当时优先中文
- 质量差距明显时，不要为中文优先保留较差资源

## 0 推荐的判断

以下情况应保持空缺，不凑数：

- 只有营销介绍、概念科普，没有实操内容
- 输出物与用户任务不符（用户要可编辑图，只找到静态展示）
- 内容已过时且找不到当前可用的替代
- 只有相近主题，需要大量解释才能勉强关联

0 推荐时简要说明最接近的候选差在哪，以及搜索方向仍缺什么。

不需要输出完整淘汰清单，除非操作者明确要求审计过程。

## Adjacent-option discipline

用户显式限定资源形式或表达"没有好的就说没有"时，有用的相邻 Tool / Case 可单独提及，但除非用户允许替换，否则不得占推荐位。

## Official user resource vs evidence anchor

官方资料有两种角色：

- **user resource**：本身就能帮用户完成任务，可以占推荐位
- **evidence anchor**：只用于核验第三方说法，不占推荐位

不能因为"是官方"就自动占一个推荐位；官方资料如果对用户任务没有直接帮助，它只是证据锚点。

对配置 / API / 版本类问题，官方资料常常同时是两者，此时当然可以推荐。

## 社区信号只是弱证据

Star、点赞、收藏、阅读量可以回答"是否有人关注"，不能回答"是否适合当前任务"。

不设固定 Star 阈值：不因为 0 Star 自动淘汰，也不因为高 Star 自动推荐。

## 厂商自述数字

厂商案例中的性能、成本、效率提升数字属于**来源自述**。引用时必须注明是厂商声称，不得改写成独立验证的事实。
