# 采用一致性检查

只在以下情况读取：**已经识别出一个具体能力缺口，但准备输出“无需专门资源 / 继续当前 AI / C 类低成本路径”时。**

目的不是强迫推荐工具，而是防止 General-AI-first 滑成 General-AI-almost-always。

依次检查：

1. **缺口是否真实可观察？**
   - 当前 AI/Agent 是否确实拿不到关键系统/仓库事实、无法稳定交付所需格式、无法承担确定性处理，或在重复规模下产生明显返工？
   - “某工具功能更多”不算能力缺口。

2. **当前 baseline 到底是什么？**
   - 比较对象是用户已经能用的 AI / Agent / 内部工具 / exporter / workflow，不是裸模型。
   - 如果现有工具已经覆盖缺口，优先 A。

3. **是否存在直接命中缺口的专门能力？**
   - 例如系统/仓库真实访问、专业可编辑格式、确定性校验、批量维护/差异更新、受控本地执行。
   - 不要用 ERP 场景标签替代能力匹配。

4. **收益是否值得采用成本？**
   - 同时考虑安装、学习、迁移、权限、数据外发、维护和治理成本。

据此校准：

- 缺口不成立或 baseline 已覆盖 → **A**；
- 缺口成立，专门能力直接命中，且预期收益足以覆盖采用成本 → **B** 或条件化 B；
- 缺口成立，但当前规模/频率/采用成本使重方案暂不值得 → **C**，给最低成本学习/采用路径和升级信号；
- 关键事实缺失且不同答案会改变 A/B/C → **显式未知项/条件分支**，不要用 C 代替“信息不足”。

### C 的额外约束

C 不等于“让用户替我们测试工具”。

只有某个技术不确定性满足以下条件时才设计最小验证：

- 它会直接改变采用判断；
- 静态/当前证据无法解决；
- 验证成本低于错误采用成本。

否则，C 应停在低成本学习/采用路径与升级信号。

最后问：

> **如果 Specialized resource 写成 none / A / C，我能否明确解释为什么这个已经观察到的能力缺口仍不值得进入 B？**

解释不成立，就重新判断；不要为了克制而克制。
