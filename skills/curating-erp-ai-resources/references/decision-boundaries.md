# 决策边界示例

只在 A/B/C 边界不清、担心过度工具化或需要校准判断时读取。本文件提供**判断模式**，不是 ERP 场景到工具的答案表。

## 1. 普通 AI 已经够用

**情境**：用户已有完整会议纪要和模板，只需要整理成一份可评审文档；现有 Agent 能读取材料并输出所需格式，没有系统访问、专业编辑器或确定性计算缺口。

**判断**：A。直接给 `输入 → 操作 → 输出 → 复核` 工作方式，不搜索新 Skill。

**常见错误**：因为任务叫“需求分析”就去找 BA/PM Skill。

## 2. 专门能力解决明确交付缺口

**情境**：业务流程语义已经明确，但必须交付可编辑、可继续维护的专业流程文件；普通对话输出会产生明显格式返工。

**判断**：B。围绕“可编辑专业交付格式”比较专门能力。

**常见错误**：把“流程图”本身当作触发固定工具的标签，而没有确认真正瓶颈。

## 3. 系统访问能力才是瓶颈

**情境**：用户要理解一个真实代码库或 ERP 系统对象，普通 Agent 可以解释概念，但关键结论依赖仓库符号、where-used、配置或系统元数据。

**判断**：先利用现有 repo/file 能力；只有缺少真实访问能力时再升级 Tool/MCP。重要结论必须回到源码、配置、测试或系统证据。

**常见错误**：把模型知识或生成的 FS 当成系统事实。

## 4. 先低成本试验，而不是直接采用复杂方案

**情境**：某专门方案可能更强，但安装、权限、迁移或企业审批成本高，当前任务规模很小，收益尚不明确。

**判断**：C。先用现有 Agent 做一个最小真实样本，并定义什么结果出现后值得升级。

**常见错误**：因为候选功能更多就直接推荐长期采用。

## 5. 外部资源不是越多越好

**情境**：已经找到一个能展示真实输入、操作步骤、输出、限制，并通过关键当前事实核验的资源；第二、第三个候选没有提供新的决策边界。

**判断**：停止。默认保留 0–1 个主资源。

**常见错误**：为了“覆盖全面”继续堆链接。

## 6. Runtime test 是决策工具，不是仪式

**应该测试**：两种方案的权限、隐私、兼容或真实输出差异会直接改变推荐，而静态证据无法解决。

**不应该测试**：已有证据足以确定下一步，只是为了让报告看起来更严谨。

## 最终校准

不要问“这个场景通常用什么工具”。优先问：

> **现有 AI 在这个真实任务上具体缺了什么？这个缺口是否大到值得付出新增能力的成本？**
