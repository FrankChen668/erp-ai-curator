# 决策边界示例

只在 A/B/C 边界不清、担心过度/不足工具化时读取。本文件提供**判断模式**，不是 ERP 场景到工具的答案表。

## 1. A — 当前工具链已经够用

**情境**：用户已有完整会议纪要和模板，只需要整理成可评审文档；现有 Agent 能读取材料并输出所需格式，没有系统访问、专业编辑器或确定性计算缺口。

**判断**：A。不搜索新 Skill；给最低成本的现有工具链做法。

**常见错误**：因为任务叫“需求分析”就去找 BA/PM Skill。

## 2. B — 专门能力解决明确交付缺口

**情境**：业务流程语义已经明确，但必须交付可编辑、可继续维护的专业流程文件；普通对话输出会产生明显格式返工。

**判断**：B。围绕“可编辑专业交付格式”发现专门能力，而不是围绕“流程图”标签搜索工具。

**常见错误**：只要看到某个强工具功能更多，就忽略用户现有工具链已经能完成大部分任务。

## 3. B / 条件化 B — 真实系统访问才是瓶颈

**情境**：用户要理解真实代码库或 ERP 系统对象，普通 Agent 可以解释概念，但关键结论依赖仓库符号、where-used、配置或系统元数据。

**判断**：先利用用户已经有的 repo/file 能力；只有缺少真实访问能力且该缺口会改变结论时，再升级 Tool/MCP。重要结论必须回到源码、配置、测试或系统证据。

**常见错误**：把模型知识或生成的 FS 当成系统事实；或因为 MCP 能写入就默认授予写权限。

## 4. C — 暂不值得复杂化

**情境**：某专门方案可能更强，但安装、权限、迁移、企业审批或长期维护成本较高，而当前任务规模/频率尚不足以证明这些成本值得。

**判断**：C。先给最低成本的学习/采用路径，并写清出现什么可观察瓶颈后再升级到 B。

**不自动要求用户跑测试。**只有某个技术不确定性确实会改变采用判断、且现有证据无法解决时，才做最小验证。

**常见错误**：

- 把“我缺信息”写成 C；
- 因为不敢判断就让用户先测试所有候选；
- 因为候选功能更多就直接推荐长期采用。

## 5. 信息不足不是第四种 C

**情境**：是否允许云端、目标 EBS/SAP 版本、真实交付格式等未知事实会直接改变推荐。

**判断**：写条件分支或显式未知项；如果当前已有一个不依赖这些未知项的稳定建议，可以先给稳定部分。

**常见错误**：用“先低成本试试”掩盖真正会改变 A/B/C 的信息缺失。

## 6. 外部资源不是越多越好

**情境**：已经找到一个能展示真实输入、操作、输出和限制，并完成关键事实核验的资源；第二、第三个候选没有新增采用边界。

**判断**：停止。默认保留 0–1 个主资源。

**常见错误**：为了“全面”继续堆链接或按平台配额搜索。

## 7. Runtime test 是决策工具，不是仪式

**应该测试**：两种方案的权限、隐私、兼容或真实输出差异会直接改变推荐，而静态证据无法解决。

**不应该测试**：已有证据足以确定值得借鉴的实践，只是为了让报告看起来更严谨或为了获得 Pilot 数据。

## 最终校准

不要问“这个场景通常用什么工具”。优先问：

> **用户当前工具链在这个真实任务上具体缺了什么？这个缺口是否大到值得支付新增能力的采用成本？**
