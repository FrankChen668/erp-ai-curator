# 来源与搜索策略

## 第一原则：围绕用户动作搜，不围绕关键词堆结果

搜索前必须已有 `topic_intent` 与 `out_of_scope`。

每个候选最后都要回答三件事：

> 它是什么资源类型？它是否直接帮助目标角色完成本主题动作？它实际产出的结果是否就是本主题需要的结果？

“有 SAP/Oracle/AI 字样”不等于适配主题。

## 来源层级

### Tier A：官方/原始
用于事实锚定：官方文档、官方博客、Release、原始 GitHub 仓库、Skill 原始页、原作者项目页。

### Tier B：高质量实践
用于“怎么做”：完整实操文章、视频、工程笔记、真实案例。

### Tier C：发现源
小红书、普通公众号、社区帖子、榜单等。可用于发现，但需要核验正文和原创性。

### Tier D：线索
搜索摘要、二次聚合、无法确认原作者的转载。不能作为最终事实依据。

## 查询矩阵

一个主题至少覆盖这些查询意图中的 3 类：

1. 用户动作：`<角色/任务> <目标动作> <期望输出>`
2. 精确主题：`<工具/任务/Skill> <目标动作>`
3. 实操：`教程 / 实战 / 配置 / 安装 / 避坑 / guide / setup / workflow`
4. 原始：官方域名、`site:github.com`、仓库名、原作者
5. 时效：当前年份、版本、`latest / 新版 / migration / deprecated`
6. 反例/问题：`issue / broken / 不可用 / 坑 / 失败 / compatibility`

中文先搜；GitHub、CLI、MCP、Agent、模型配置至少补一轮英文。

## 对 volatile 配置教程的强制双轨搜索

必须同时建立：

- Track A：当前官方/原始事实锚点；
- Track B：第三方实操候选。

先知道“现在官方怎么说”，再评价第三方教程。

不能反过来先相信教程，再去找能支持它的证据。

## 平台能力现实

不要假设 WebSearch/WebFetch 能完整抓取所有平台。

- 官方站/GitHub：通常可做 Tier A 核验。
- B站：如果能获得正文/字幕可 content_checked；只能看到标题/简介则 metadata_only。
- 微信公众号/小红书：常见登录、反爬或正文访问限制；没有专用浏览器/MCP时以发现候选为主。
- 需要登录、验证码或专用 App 的内容：禁止绕过；进入人工复核。

## GitHub 强制检查

不要只看 Star。每个进入幸存者池的 GitHub 候选必须尽量检查：

- `fork` 是否为 true；
- 若 fork，parent/source 是谁；
- upstream 是否明显更活跃/更权威；
- README 是否有实际使用方式；
- 最近 Release/提交；
- Issue 是否暴露明显不可用；
- 适配工具/版本；
- License（如果后续需要复用，而不只是链接）。

**未解析 upstream 的 fork 不得首推。**

## 视频/文章检查

重点：
- 发布时间与版本；
- 是否真的展示操作过程；
- 是否说明前置条件和失败处理；
- 是否只是成品演示/营销；
- 是否可被当前用户环境复现；
- 是否存在需要官方核验的 material claims；
- 是否为转载/洗稿。

## 搜索停止

达到覆盖目标后，连续两类新查询没有出现同槽明显强于当前幸存者的资源即可停止；不要为“全面”无限搜索。

如果搜索预算耗尽仍没有 Gate 全 PASS 的候选，结论就是 **0 推荐**，而不是降低门槛。
